Lesson 1 · Refunds in Cadence

The life of a refund request

What the learner sees, what we see, and where the road ends.

Today a learner can ask for a refund, but nobody can answer. The request half is built. The approval half is not.

By the end you should be able to walk through the flow from memory and say exactly where it stops. Interfaces below are redrawn from the code, using the seeded learner Liam as the example.

1. The learner requests a refund

An enrolled learner opens the course page. If the purchase qualifies, a quiet Request a refund button sits at the bottom of the sidebar. Clicking it opens a form that needs a reason of 10 to 1000 characters.

The purchase qualifies only if all of these hold: it is within 14 days, the learner has watched under 2 hours, no team seat from it has been claimed, and no request is already open. The button also hides at 50% of lessons completed.

Source: courses.$slug.tsx lines 450–499 (who gets offered) and 1003–1064 (the form).

2. The request goes through the system

The form posts to a route action that runs on the server. In order, it:

  1. Re-checks who is asking and whether the purchase is eligible.
  2. Writes one row to the refund_requests table.
  3. Builds a confirmation email to the learner and prints it to the server log, because no mail service is connected.
  4. Redirects the learner to Settings.

The row holds the purchase, the reason, the time, and status = requested. That row is the only lasting record of the request.

Source: courses.$slug.refund.ts lines 114–241.

You asked how we get notified: we don't. The only traces are the database row and a server log line addressed to the learner, and that log line doesn't include their reason.

On the course page the Request a refund button disappears, but nothing says a request is open. The learner keeps full access, because the action never touches their enrollment.

Source: settings.tsx lines 58–76 and 209–243.

4. How we approve it

We can't. The admin area has Users, Courses and Categories, with no refund page. No code anywhere writes approved or declined. The app also has no payment provider, so there is no charge to send back, whatever the form promises about the card.

The design is sketched in the schema (lines 34–38 and 232–254), which has the statuses and three columns that are always empty today: amount_refunded, resolved_at, resolved_by_user_id.

5. How the interfaces change afterwards

They don't, because no approval can happen. But the existing queries tell us what would happen if someone changed the status by hand, since they only ever look for requested:

  • The Settings card would vanish without any "approved" message.
  • The learner would keep the course.
  • If they were still eligible, the Request a refund button would come back and they could ask again.

Check yourself

Try these from memory, without scrolling up.

1. A learner submits a valid request. What do staff receive?

The only email is built for the learner, and it goes to the server log. Staff get no alert.

2. Where does the learner see that their request is waiting?

The Settings page lists open requests. The course page only loses its Request a refund button.

3. Liam's request is pending. What can Liam do with the course?

The action adds a refund row and leaves the enrollment alone, so access is unchanged.

4. Which values of status does the application ever write today?

The enum defines three values, but only requested is ever saved. The other two are unused.
