# Which existing Cadence events could trigger a Notification?

Research for the Notifications wayfinder. Rule: only notify about things that **already exist** in Cadence. This is an inventory of every state-changing action the app performs today (every route `action` and every write in `app/lib`), sorted by whether it could concern someone other than the actor, or give the actor a record worth keeping. No new features are proposed.

Sources are the code at commit `08ed53f`. Line numbers are for that commit. Role names follow `GLOSSARY.md`. In code, a Platform Admin is `UserRole.Admin` (`app/db/schema.ts:11-15`) and a Team Admin is `TeamMemberRole.Admin` (`app/db/schema.ts:40-43`).

## How email works today

- There is one sender, `sendEmail` (`app/lib/mailer.server.ts:67-72`). It uses Postmark when `POSTMARK_SERVER_TOKEN` is set and otherwise writes JSON files to `.outbox/` (`:62-65`). Emails are plain text with `to`, `subject` and `body` (`:9-13`).
- It is called from **exactly two places**: `app/routes/courses.$slug.refund.ts:75` and `app/routes/admin.refunds.tsx:130`. Both send an email that `app/lib/refunds.server.ts` builds and returns as part of its result.
- **Purchases send no email today.** `enrollUser` takes a `sendEmail` flag, but behind it there is only a stub comment, `// Would send welcome email here` (`app/routes/courses.$slug.purchase.tsx:173-175`). The purchase action also calls it with `sendEmail = false` (`:371`). The ticket assumed purchase emails exist. They don't.

## C. Explicitly poor or out-of-scope triggers

- **Lesson created / edited / moved / deleted; module add/rename/reorder/delete** (`instructor.$courseId.tsx:722-842`; lesson content `instructor.$courseId.lessons.$lessonId.tsx:207+`). Lessons have no publish step: a lesson is live the moment it's saved, so "new lesson" would fire on every draft edit. Out of scope.
- **Quizzes**, both authoring (`instructor.$courseId.lessons.$lessonId.quiz.tsx:337-430`) and attempts/results (`courses.$slug.lessons.$lessonId.tsx:603-620, 952+`). Out of scope.
- **Categories** create/rename/delete (`admin.categories.tsx:191-215`). Platform-admin housekeeping. A category in use can't be deleted (`:125-129`). Nobody else is concerned.

## D. Things the ticket asked about that do **not** exist today

- **Pending / Issued / Failed Refund.** These are defined in `GLOSSARY.md`, but no code models them. `RefundStatus` is only `open | approved | declined` (`app/db/schema.ts:34-38`). There is no payout integration, and nothing in `app/` mentions issued/failed refunds or a payment provider. ADR 0002 says money movement "is handled separately". Under the "only what already exists" rule, Refund outcomes beyond approve/decline are **not** available triggers.
- **Team membership changes.** The only write to `team_members` is the automatic Team Admin row on a buyer's first Team Licence (`courses.$slug.purchase.tsx:210-220`). `/team` (`app/routes/team.tsx`) has no `action`. There is no add/remove member, and claiming a Seat doesn't create a membership.
- **Purchase / welcome emails.** Stub only (see "How email works today").
- **Enrollment ended other than by refund approval.** None (A11).
- **Course ownership transfer.** Nothing writes `courses.instructorId` after creation.
- **Question gone stale.** Computed for display only (A3).
- **Coupon redemption** separate from a Seat claim. A "coupon" in the code *is* a Seat (`coupons` table; the glossary says to avoid "Coupon"). `redeem.$code.tsx` is A5.

## Summary

Concerns another person and already exists: A1 reply, A2 staff answer, A3 new question, A4 staff deletes a comment, A5 Seat claimed, A6/A7 purchases (to the Instructor; a receipt to the buyer), A8 Refund Request raised (to Platform Admins), A9/A10 decided, A12 role changed, A13 admin edited profile, A14 course status changed by a Platform Admin, A15 rating.

Already emailed today: only A8 (to the buyer), A9 and A10 (to the buyer). Every email in Cadence goes to the buyer about their own Refund Request. No email goes to an Instructor, a Platform Admin or a Team Admin about someone else's action.

Note: the `Notification` glossary entry is an uncommitted change on the `wayfinder-notifications` branch, not in `08ed53f`.
